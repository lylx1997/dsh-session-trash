# v0.8 附件回收：删除安全门槛（设计稿）

> 状态：0.8.0 已发布（2a 计划/preview + 2b 执行/UI）。
> 范围：只删除 `<DSH_HOME>/attachments/v1` 下**没有任何会话引用**的附件对象；不删除会话日志、投影缓存、搜索索引或工作区文件。
> 前置：v0.8 第一刀的只读引用扫描已合入，`/state.storage.attachments` 已能给出 `referencedBytes` / `orphanBytes` / `complete` / `scan`。

## 0. 决策摘要

按“用户体验优先、实现成本其次、心智负担尽量低”定下：

| 议题 | 决定 |
|---|---|
| 5 分钟等待 | **不要**。preview 生成计划后立即可执行；计划 15 分钟内有效。安全性由日志指纹 + 24 小时对象年龄 + 执行时重扫保证。 |
| `missing` 条目 | **不静默阻塞**。preview 返回 `TRASH_HAS_MISSING` 和缺失列表，弹窗提供「移除缺失记录并继续」一键处理，然后自动重新 preview。 |
| 是否要求单实例 | **不阻塞**。确认框里放一行提示“建议先关闭其他 DSH 窗口；回收期间新增会话会让清理自动中止”。 |
| quarantine / undo | **v0.8 不做**。删除即不可恢复，用二次确认 + 审计日志。quarantine 留到 0.9 视需求再评估。 |
| 新增配置 | **不新增**。24h / 15min / 50 个一批作为内部常量；只在实现层注入时钟/常量便于测试。 |
| 发现入口 | 不藏配置开关。扫描完成且 `orphanBytes > 0` 时，存储行旁边直接出现「清理无引用附件…」。 |
| 交互步数 | 点击 → 自动预览 → 输入确认短语 → 删除。无倒计时、无等待页、无额外配置。 |

## 1. 必须始终成立的不变量

| 编号 | 不变量 |
|---|---|
| I1 | 任何仍被 live、已存、回收站引用的对象，绝不删除。 |
| I2 | 引用扫描不完整（`status != complete`、`failedDirs > 0`、`failedFiles > 0`、`tornFiles > 0`）时，不删除任何对象。 |
| I3 | 附件目录读不全（`attachments.complete == false`）时，不删除任何对象。 |
| I4 | 计划生成后，只要任一相关会话日志的大小或 mtime 变化，计划立即失效，不删除。 |
| I5 | 只删除计划中列出、且仍能按已知布局解析为附件对象的哈希；`tmp/`、未知布局、符号链接、`unclassified` 一律不碰。 |
| I6 | 删除是可中断、可重试、幂等的；失败不会破坏仍被引用的对象。 |
| I7 | 删除范围严格限制在 `<DSH_HOME>/attachments/v1` 下，绝不删除用户工作区或 DSH 其他数据。 |
| I8 | 只能由用户手动触发；没有自动回收、没有定时回收。 |

## 2. 为什么不要“等等再删”

- 5 分钟等待对用户的收益很低：用户点完还要回来，容易以为卡住；而它并不能真正消灭竞态。
- 真正保护引用的是**日志指纹**：计划时记录所有日志的 `(path,size,mtime)` 指纹；执行前重扫，指纹一变就整体作废。任何新引用都必须写入日志，因此会被发现。
- 对象年龄 24 小时保护“刚上传/刚粘贴但尚未落盘”的对象；计划 + 确认短语 + 审计覆盖误操作。
- 所以：**预览后立即可以确认**；计划 15 分钟过期只是防止用户很久以前点的确认被误用，不是强制等待。

## 3. 四层安全门

### G0：产品门（手动 + 明确确认）

- 没有 `enableAttachmentReclaim` 开关；扫描完整且 `orphanBytes > 0` 时，页面显示入口。
- 没有自动/定时回收。
- 确认框必须输入本地化短语（中文“删除附件” / 英文 `delete attachments`）；API 请求同时带固定短语 `delete-unreferenced-attachments`。
- 确认框明确写：永久删除、不可恢复、只删无引用对象、不删会话日志和其他数据。

### G1：根集合门（生成计划前）

按顺序执行，任何一步失败即中止：

1. **拿 `.lock`**：和 trash/restore/purge 共用同一把跨进程锁。
2. **拒绝保护模式**：`store.isProtected()` 为 true 时中止。
3. **先自动整理回收站**：调用现有 `recover()` 处理 `trashing/restoring/purging`。
   - 整理后仍有这些状态 → `TRASH_BUSY`，弹窗提示“回收站正在整理，请稍后重试”。
   - `missing` 不自动处理；由 UI 提供「移除缺失记录并继续」。
4. **刷新 live 会话**：调用 `ctx.sessionPersistence.flush()`；失败即 `SESSION_FLUSH_FAILED`。
   - 让当前回合已提交的事件落盘，引用扫描才能看见。
5. **完整扫描**：`references.scan({ force: true })`。要求：
   - `status === "complete"`
   - `failedFiles === 0`
   - `failedDirs === 0`
   - `tornFiles === 0`
   - `attachments.complete === true`
6. **根覆盖校验**：扫描到的日志路径必须覆盖：
   - 每个 `sessionPersistence.list()` 快照的 `location.path`（缺失时用会话 id 兜底确认）；
   - 回收站每个条目的每个成员对应的 `session/` 或 `children/<id>/` 日志。
   - 任何预期日志没被扫描到 → `ROOTS_INCOMPLETE`。
7. **计算日志指纹**：所有扫描日志按 `相对路径 + size + mtimeMs` 排序后取 SHA-256，记为 `logFingerprint`。
8. **计算候选**：无引用、对象 mtime 早于 24 小时、已知布局、非 `tmp`、非 `unclassified`。

### G2：计划门（写计划）

计划写入 `<trash-root>/reclaim/plan.json`（0600，原子写），字段见第 4 节。

- `expiresAt = createdAt + 15 分钟`；没有 `readyAt`。
- 每次 preview 原子替换旧计划；旧计划立即失效。
- 计划只包含候选对象的哈希、字节、store、mtime 和相对别名；不返回绝对路径。
- 计划文件很小，页面刷新后可用 `GET /reclaim/plan` 恢复摘要；过期则提示重新预览。

### G3：执行门（真正删除前）

1. 重新拿 `.lock`。
2. 读取计划；`now > expiresAt` → `PLAN_EXPIRED`。
3. 再次执行 G1 的 2–7 步（自动整理、flush、完整扫描、根覆盖）。
4. 对比 `logFingerprint`：不一致即 `PLAN_STALE`，不删任何对象，计划标记失效；页面提示“有会话更新，请重新预览”。
5. 对每个候选哈希按当前磁盘状态重新枚举别名；对象 mtime 变化则跳过。
6. 分批删除（50 个/批）：
   - **每批开始前**重新 stat 日志并计算轻量指纹；变了立即停止后续批次。
   - 批次内逐对象执行第 6 节的删除算法。
7. 写审计日志；返回实际删除、跳过、失败。

### G4：对象级门（删除单个对象时）

- 哈希必须在计划中。
- 哈希在最新引用集合中不存在。
- 对象 mtime 早于 24 小时。
- 所有别名都在 `attachments/v1` 的已知布局内；`lstat` 必须是普通文件，不跟随符号链接。
- `nlink` 必须等于已知别名数量。多出来的链接说明有未知别名（例如手工硬链接），跳过并报告 `linked-elsewhere`；少则状态不一致，跳过。
- 绝不删除 `tmp/`、无法解析哈希的文件、`unclassified` 文件。
- 删除顺序：先删 `files/<hash>/<name>` 别名，最后删 `file-objects/<hash>` / `objects/<2>/<hash>`；全部别名都删成功才计入释放字节。
- 删除后尝试 `rmdir` 空的 `files/<hash>` 目录（非空则保留），不删两位分片目录。

## 4. 计划文件与审计日志

```text
<DSH_HOME>/.session-trash/

    reclaim-log.jsonl      # 追加式审计
```

    "status": "complete",

## 5. API 草案

路由位于 `/plugins/dsh-session-trash/api/`，沿用现有鉴权、CSRF、64 KiB 限制。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/reclaim/preview` | 无请求体；执行 G1/G2，写计划，返回 `{ ok, plan: { id, createdAt, expiresAt, totals, byStore, scan, eligible, reason?, missing? } }` |
| `GET` | `/reclaim/plan` | 返回当前计划摘要；无计划返回 `{ ok: true, plan: null }` |
| `POST` | `/reclaim` | `{ planId, confirmation: "delete-unreferenced-attachments" }`；执行 G3/G4 |
| `POST` | `/reclaim/cancel` | 删除计划文件；不删附件 |

`preview` 的 `eligible: false` 情形（仍返回 200）：

- `SCAN_UNAVAILABLE`：没有 zstd 解码器（Node 20）。
- `SCAN_INCOMPLETE`：扫描 partial / 有失败目录 / 有撕裂尾部。
- `ATTACHMENTS_INCOMPLETE`：附件目录读不全。
- `TRASH_BUSY`：回收站还有 `trashing/restoring/purging`。
- `TRASH_HAS_MISSING`：有 `missing` 记录，附 `missing: [{ sessionId, title }]`，客户端可一键 forget 后重试。
- `ROOTS_INCOMPLETE`：有预期日志没被扫描到。
- `NOTHING_TO_RECLAIM`：没有超过 24 小时的无引用对象。

`reclaim` 成功响应：

```json
{
  "ok": true,
  "planId": "...",
  "deleted": { "hashes": 130, "bytes": 45200000 },
  "skipped": [{ "reason": "referenced" }, { "reason": "linked-elsewhere" }],
  "failed": [{ "reason": "unlink-failed" }],
  "scan": { "status": "complete", "at": 1794650300000 }
}
```

执行错误码：`CONFIRMATION_REQUIRED`、`PLAN_NOT_FOUND`、`PLAN_EXPIRED`、`PLAN_STALE`、`TRASH_BUSY`、`TRASH_HAS_MISSING`、`SESSION_FLUSH_FAILED`、`SCAN_INCOMPLETE`、`ROOTS_INCOMPLETE`、`NOTHING_TO_RECLAIM`、`LOCKED`、`IO_ERROR`。

## 6. 删除算法（单个哈希）

```text
candidate = plan.candidates[hash]
if refs.has(hash) -> skip("referenced")
if now - candidate.mtimeMs < 24h -> skip("too-young")

aliases = []
for store of ["objects", "file-objects", "files", "request-images"]:
  enumerate paths for this hash under store, lstat each
  skip symlinks / non-files
  aliases += relative paths

if aliases.length === 0 -> skip("missing")
if aliases.length > MAX_ALIASES (e.g. 1000) -> skip("too-many-aliases")
for alias of aliases:
  resolved = path.resolve(root, alias)
  if !isInside(root, resolved) -> skip("unsafe-path")
  stats = lstat(resolved)
  if stats.nlink !== aliases.length -> skip("linked-elsewhere")
  if stats.size !== candidate.bytes -> skip("changed")

deletedAll = true
for alias of aliases sorted with files/ first:
  try unlink(resolved)
  catch ENOENT -> continue
  catch -> deletedAll = false; record failure; break

if deletedAll:
  remove empty files/<hash> dir
  freeBytes += candidate.bytes
else:
  // 剩余别名仍可读，不算释放；下次可重试
```

说明：

- `nlink` 只适用于支持硬链接计数的文件系统；不可用或为 0 时按 `linked-elsewhere` 跳过，不做猜测。
- `files/<hash>/<name>` 名称可以多个；每个都计入 `aliases.length` 和 `nlink`。
- 中途失败时已删的别名不恢复；因为还有别名或 canonical 存在，会话读取不会损坏；审计记 `partial`。

## 7. 崩溃、并发与恢复

- **锁**：preview/execute/cancel 都在 `.lock` 下；和 trash/restore/purge 串行。
- **其他 DSH 进程**：不遵守 `.lock`。确认框放一行提示，建议先关闭其他 DSH 窗口；指纹 + 每批重检把窗口压到两次 stat 之间。
- **崩溃**：计划文件保留；重启后执行重新走 G1/G3；已删对象变 missing，自动跳过；计划 15 分钟过期；不自动删除。
- **计划损坏**：视为无计划；preview 可覆盖；不删任何对象。
- **部分失败**：记录 `failed`，其他对象继续；返回实际删除字节；下次 preview 重新计算。
- **审计不可写**：`IO_ERROR`，不开始删除（审计不可靠时不执行）。

## 8. UI 流程

入口只在 `attachments.complete === true`、`scan.status === "complete"`、`orphanBytes > 0` 时显示；否则存储行只显示原因。

1. **点击「清理无引用附件…」**：打开对话框，自动调用 `/reclaim/preview`（有未过期计划则 `GET /reclaim/plan` 复用）。
2. **预览成功**：
   - “将删除 132 个对象，释放 43.3 MB；只删除超过 24 小时、没有任何会话引用的对象。”
   - “共享附件、会话日志、投影缓存、搜索索引和工作区文件不会删除。”
   - 显示扫描时间、`tornFiles`、`failedDirs`；建议先关闭其他 DSH 窗口。
   - 输入确认短语后「永久删除」可用。
3. **没有可删对象**：说明“暂无超过 24 小时的无引用附件”，不显示确认输入。
4. **扫描不可用/不完整**：显示原因和「重新扫描」；不出现删除按钮。
5. **有 missing 记录**：显示「有 N 条日志缺失记录，无法判断其附件引用」和「移除缺失记录并继续」；点击后逐条调用现有 `/forget`，再自动重新 preview。
6. **计划过期或日志变化**：Toast “会话有更新，请重新预览”，对话框切回预览按钮。
7. **成功**：Toast “已删除 130 个无引用附件，释放 43.1 MB；跳过 2 个。” 存储行刷新。

无倒计时、无“等待 5 分钟”、无额外配置页。

## 9. 配置

**v0.8 第二刀不新增配置。** 内部常量：

| 常量 | 值 | 说明 |
|---|---:|---|
| `ATTACHMENT_GRACE_MS` | 24h | 只清理 mtime 早于 24h 的对象 |
| `PLAN_TTL_MS` | 15min | 计划有效期；过期重新预览 |
| `RECLAIM_BATCH_SIZE` | 50 | 每批对象数；批前重检指纹 |

实现层允许测试注入时钟/批量大小，但不暴露到插件 Config。
如果以后有真实需求，再增加 `attachmentGraceHours` 等高级配置；第二刀不加。

## 10. 测试矩阵

**单元**

- 计划门：保护模式、`trashing/restoring/purging` 自动整理失败、`missing` 返回列表、flush 失败、扫描 partial、`failedDirs`、`tornFiles`、附件 `complete=false`、根覆盖缺失、指纹变化、计划过期。
- 候选：共享对象、仅 trash 引用、legacy `request-images`、`unclassified`、`tmp`、刚上传（too young）、硬链接 `nlink` 异常。
- 删除：所有别名删除、`files` 多名称、canonical 最后删、部分失败、`ENOENT`、空目录清理、不会删 `tmp/unclassified`。
- 并发：`LOCKED`；执行时计划过期；preview 替换旧计划。
- 崩溃：删除中途失败；重启后重试；已删对象跳过。
- 安全不变量：删除后所有剩余日志引用仍能解析到对象；删除集合与计划一致。

**集成 / e2e**

- 临时 DSH_HOME：真实 zstd 日志 + 真实附件对象（objects、file-objects、files、legacy）。
- 共享对象：两个日志引用同一哈希，删除后仍存在。
- 孤儿：无引用且超过 24h，删除后字节减少。
- 新引用：计划后追加一条日志，执行返回 `PLAN_STALE`，不删。
- missing：preview 返回列表；forget 后重新 preview 成功。
- 真实 Host e2e：点击入口 → preview → 输入确认 → 删除 → `/state.orphanBytes` 下降；trash/restore/purge 不受影响。
- Node 20：`scan.status=unavailable` → preview `SCAN_UNAVAILABLE`，不删。

**故障注入**

- 单个 `unlink` EACCES。
- 计划文件损坏/只读。
- `.lock` 被占用。
- 审计目录不可写 → `IO_ERROR`，不删。

## 11. 分阶段实现

- **2a（preview + 计划，无删除）**：新增扫描 `fingerprint/files/force`、根覆盖、计划文件、`/reclaim/preview`、`GET /reclaim/plan`、`/reclaim/cancel`。这一刀只做后端/API 与测试；UI 预览、missing 引导、确认框和删除一起在 2b 接入，避免先给用户一个没有动作的半成品弹窗。
- **2b（执行删除）**：`/reclaim` + G3/G4 + 审计 + 确认短语 + 完整测试。
- **2c（后续，可选）**：quarantine/undo、定时策略、高级配置。

2a 不删任何文件，适合先合入；2b 在 2a 验证后再做。

## 12. 明确不做

- 不按会话级联删附件。
- 不删除仍被引用的共享对象。
- 不删除 `tmp/`、`unclassified`、未知布局、符号链接。
- 不做“预览后等待 5 分钟”。
- 不做自动回收/定时回收。
- 不删会话日志、投影缓存、搜索索引、工作区文件。
- 不假设第三方记忆/索引插件保存的副本会保护附件。
- 不做 quarantine/undo（0.8 内）。

## 13. 已定取舍与后续

- **UX 优先**：去掉配置开关和 5 分钟等待；用一次对话框完成“预览 → 确认”，把复杂度留在后台的指纹、重扫和审计。
- **保留的摩擦**：确认短语、24 小时对象年龄、扫描不完整时禁用。这些是必要的，不为了“少一次点击”牺牲数据安全。
- **未来可加**：若用户反馈需要撤销，再做 quarantine；若需要自动化，再加工信配置；当前不提前引入。
- **上游**：如果 DSH 提供 `attachments.collectGarbage(roots)` 或引用计数，应替换文件系统级实现。
